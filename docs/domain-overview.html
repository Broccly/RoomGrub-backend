How an expense becomes a settled balance

RoomGrub splits shared expenses across roommates. This page walks through every table involved in turning a purchase into a running balance, and a balance into a settlement record.

Entity map

Every expense fans out into one split row per participant, and each split shifts that member's running balance in the room.

```mermaid erDiagram USERS ||--o{ USERROOMS : "is member via" ROOMS ||--o{ USERROOMS : has ROOMS ||--o{ SPENDINGS : contains USERS ||--o{ SPENDINGS : "spent by" SPENDINGS ||--o{ SPENDINGSPLITS : "split across" USERS ||--o{ SPENDINGSPLITS : participates ROOMS ||--o{ ROOMBALANCESUMMARY : "net position in" USERS ||--o{ ROOMBALANCESUMMARY : "owes / is owed" SPENDINGS { int user_id "payer" int money bool settled timestamp settled_at } SPENDINGSPLITS { decimal amount_paid decimal amount_owed } ROOMBALANCESUMMARY { decimal pending_amount timestamp settled_at "null = active row" } ```

Splits & balances

Participants are chosen explicitly per expense. The split and running balance are computed once, at write time — reads become a single indexed lookup instead of a live aggregation.

SpendingSplits

One row per participant per expense. A row's existence is the participation record — net isn't stored, just computed as amount_paid − amount_owed.

FieldNote
spending_id→ Spendings.id
user_id→ Users.id
amount_paidnon-zero only on payer's row
amount_owedmoney ÷ participant count

RoomBalanceSummary

A historical ledger, not a snapshot: one active row per member per room, plus any number of closed rows from past settle-alls.

Write & read flow

What happens the moment someone adds a grocery run, and what happens when someone checks the room's balances.

Add expense

Payer picks participants explicitly (or none → defaults to all current room members).

Compute split

Even division across chosen participants; one SpendingSplits row per participant, written in the same transaction.

Update balance

Each affected member's active RoomBalanceSummary row shifts by their share — no full-room recompute. The other participants then get a push notification.

Read

GET /splits reads the active rows straight from Postgres — one indexed query, not a live aggregation.

Who pays whom

Computed on the fly from the small set of active rows via greedy debt-simplification — not persisted as pairwise rows.

Settlement, as history

Settling never deletes anything — the balance row that was live becomes the record of the settlement.

Settle-all (admin, whole room): the server first checks the balances the client is showing against its own, within 0.01. Then every active row is stamped settled_at = now() and frozen in place as a permanent record — "this much was owed, settled at this time." A brand-new active row opens at pending_amount = 0 for each current member, and the room's unsettled expenses are marked settled.

Settlement is all-or-nothing per room: there is no single-member or partial settle. The closed rows are stored, but no endpoint lists them yet.

What it replaced removed

Before July 2026 every split was computed live, on every read, dividing evenly across all current room members — there was no record of who actually took part in an expense.

balance

dropped

Settlement + contribution ledger. Rows were consumed and deleted as settlements happened, so no history survived. Dropped in migration 20260718165615.

"Contribute"

removed, no replacement

A member could add money to the room without an expense. Not carried forward.

Single-member & filtered settle

removed

Settling one member, a date range or a subset of members. Only settle-all remains.
