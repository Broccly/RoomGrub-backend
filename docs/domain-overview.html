How an expense becomes a settled balance

RoomGrub splits shared expenses across roommates. This page walks through every table involved — what's live in production today, what's being phased out, and the new participant-aware, precomputed-balance domain replacing it.

Legacy ledger being removed

Every split is computed live, every read, dividing evenly across all current room members — there's no record of who actually participated in a given expense.

"Contribute"

removed, no replacement

A member could add money to the room without an expense. Route, schema, service, and model function are deleted outright in Phase 2 — this capability is not carried forward.

New domain rolling out

Participants are chosen explicitly per expense. The split and running balance are computed once, at write time — reads become a single indexed lookup instead of a live aggregation.

SpendingSplits

new

One row per participant per expense. A row's existence is the participation record — net isn't stored, just computed as amount_paid − amount_owed.

Write & read flow

What happens the moment someone adds a grocery run, and what happens when someone checks the room's balances.

Add expense

Payer picks participants explicitly (or none → defaults to all current room members, matching legacy behavior).

Compute split

Even division across chosen participants; one SpendingSplits row per participant, written in the same transaction.

Update balance

Each affected member's active RoomBalanceSummary row shifts by their share — no full-room recompute.

Read (cached)

Redis cache-aside in front of the active rows. Miss → one indexed query, not a live aggregation.

Who pays whom

Computed on the fly from the small set of active rows via greedy debt-simplification — not persisted as pairwise rows.

Settlement, as history

The old ledger deleted its adjustment rows as it consumed them — there was never a record of past settlements. The new active/closed-row model fixes that.

Full settle (one member, or settle-all): the active row is stamped settled_at = now() and frozen in place as a permanent record — "this much was owed, settled at this time." A brand-new active row opens at pending_amount = 0. Members can page back through their closed rows to see every past settlement.

Partial / filtered settle only updates the active row's pending_amount in place — it's not a close-out event, since the balance isn't fully zeroed.

Rollout phases

Additive schema first, dual-write in shadow mode, then cache-aside reads, then cut the old path loose.

Phase 0

Schema

Add SpendingSplits, RoomBalanceSummary, Spendings.settled_at. Nothing existing altered.

Phase 1

Backfill

Legacy expenses get participants = current room members, even split. Spot-checked against live totals.

Phase 2

Shadow write

New tables written alongside old reads. Contribute feature removed outright.

Phase 3

Cache-aside reads

GET /splits cuts over to RoomBalanceSummary + Redis. Settle wired to close/reopen.

Phase 4

API surface

Expose per-expense participant/split detail endpoint.

Phase 5

Cutover

Old live-aggregation code deleted. balance table dropped once reference-free.
