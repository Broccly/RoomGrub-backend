# RoomGrub Backend — Guest Access & Growth (design spec)

**Status: planned — nothing in this document is built yet.** It is the design for [PLAN.md](PLAN.md) Phase 12. The checklist is in [TODOS.md](TODOS.md). [DOMAIN.md](DOMAIN.md), [AUTH.md](AUTH.md) and [ARCHITECTURE.md](ARCHITECTURE.md) keep describing what is built today. When a phase below ships, move its rules into those docs and mark the phase done here.

---

## Why

Two things hold back growth:

1. **You must sign in before you can do anything.** Using the app requires a Google or Facebook account.
2. **A group can't start until everyone accepts an invite.** You can't split with a friend until they install the app, sign in and accept.

## Features

| # | Feature | Phase |
|---|---------|-------|
| 1 | Use the app as a **guest** with only a name (required) and an optional avatar. A guest can do everything a signed-in user can | C |
| 2 | Every user, guest or signed in, can **edit their own name and avatar** | B |
| 3 | An Admin, guest or signed in, can **add a friend to a room by name only**, to split expenses with them | D |
| 4 | A room gets a **name** when it is created | B |
| 5 | A room can be shared through a **public link** | E |
| 6 | A guest can **sign in later** and keep the same account and data | F |

Phase A is groundwork that the other phases depend on.

## Core design: guests are ordinary `Users` rows

Splits, balances, memberships, room guards and push are all keyed on `Users.id`. If guests are normal `Users` rows, the expense → split → balance → settle engine works for them unchanged. A column, `Users.type`, tells the kinds of user apart:

| `type` | Who | Credentials | Created by |
|--------|-----|-------------|------------|
| `registered` | A Google/Facebook user, as today | Provider login, then RoomGrub tokens | `POST /auth/login` |
| `guest` | A self-onboarded person with a name only (feature 1) | RoomGrub tokens only, held by the device that created it | `POST /auth/guest` |
| `placeholder` | A friend an Admin added by name (feature 3) | None. Cannot sign in until someone claims it | `POST /rooms/{room_id}/members/guests` |

A `guest` gets the same access + refresh token pair as a registered user. `get_current_user`, the room guards and the refresh-token flow need no new paths.

## Phase A: remove the email dependency — done

Migration `20261030120000_users_type_and_room_cleanup`, plus the code changes below. No visible change for existing clients; the API only gained fields.

**Schema**
- `Users.type text NOT NULL DEFAULT 'registered'`, `CHECK (type IN ('registered', 'guest', 'placeholder'))`.
- `Users.email` is nullable with no default; `''` became `NULL`. `UNIQUE` allows many `NULL`s.
- `Users_profile_key` (one avatar per user) is dropped.
- `Users.uid` and `Rooms.uid` are stable UUIDs generated by the column default on insert (`NOT NULL`, unique). All existing values were regenerated; login no longer rewrites `Users.uid`.
- `Spendings."user"` (legacy payer email) is nullable. It is still written when the payer has an email; nothing reads it.
- `Rooms.name` exists everywhere (Supabase lacked it). It is exposed in Phase B.
- Dropped the legacy `Rooms.members`, `budget`, `admin` (with `Rooms_admin_fkey`) and `Users.role`, plus the two Supabase RLS policies on `Spendings` that read `Users.role`. These only existed in Supabase, so the migration is written with `IF [NOT] EXISTS`.

**Code**
- Payer lookups use `Spendings.user_id`: expense list/detail (the API `user` field is now `Users.email` via `user_id`), the `user_email` filter, member detail totals, dashboard stats and `GET /splits` unsettled expenses.
- Settle-all accepts `user_id` or `user_email` per member.
- `GET /rooms/{room_id}/expenses` takes a `user_id` filter.
- Room responses gain `admin_user_id` and `admin_name`; all three admin fields describe the longest-standing Admin.
- The access token's `email` claim is left out when the user has no email (nothing reads it).
- Every email field in responses is `str | None`.

**Moved out of Phase A:** `Users.created_by` → Phase D; `type` on `get_current_user` → Phase C (nothing reads it yet).

## Phase B: room names and profile edits (features 4 and 2)

**Room name**
- `POST /rooms` takes an optional body `{ "name": str }`, 1–50 characters after trimming. It is optional on the server because current clients send no body. The new clients make it required in the UI.
- `name` is added to `RoomResponse`, so it appears in the list, create, summary and dashboard responses. It is `null` for old rooms; clients show a fallback.
- `PATCH /rooms/{room_id}` `{ "name" }` lets an Admin rename the room.

**Profile**
- New domain `users` with `PATCH /api/v1/users/me` `{ "name"?, "avatar"? }` and `GET /api/v1/users/me`, open to any authenticated user.
  - `name`: 1–50 characters after trimming, never empty.
  - `avatar`: stored in `Users.profile`. See open decision 4 for what values are allowed.
  - Invalidates `auth:user:{id}`.
- `upsert_user` on login fills `name` and `profile` only when they are empty. It no longer overwrites an edited profile with the provider's values. **This is a behaviour change**; note it in the CHANGELOG.
- Login also invalidates `auth:user:{id}`. This closes the existing TODO.

## Phase C: guest sign-up (feature 1)

- `POST /api/v1/auth/guest` `{ "name", "avatar"? }`, public:
  - creates a `Users` row with `type = 'guest'` and `email = NULL` (`uid` comes from the column default);
  - adds `type` to the `get_current_user` dict and its cached `auth:user:{id}` payload (a cached entry without it is a pre-Phase-C registered user);
  - starts a refresh-token family and returns the same body as `/auth/login`.
  - No `welcome` event, since there is no email address to send it to.
- From then on the guest uses `/auth/refresh` and `/auth/logout` exactly like a registered user.
- A guest can do everything a registered user can: create rooms (and so be an Admin), add expenses, join rooms, and register an FCM token.
- **Abuse control:** this is the first public endpoint that creates rows. Add a per-IP rate limit, Redis-backed and fail-open, consistent with the "Redis is never a dependency" rule. Possibly reuse it for `/auth/login` and `/join`.
- **Session loss:** the device's refresh token is a guest's only credential. Uninstalling the app, clearing its data, or the 90-day idle window ending loses the account. The apps should prompt guests to link an account (Phase F) at good moments, such as after creating a room or adding a first expense. See open decision 2.

## Phase D: friends added by name (feature 3)

- `POST /api/v1/rooms/{room_id}/members/guests` `{ "name", "avatar"? }`, Admin only:
  - creates a `Users` row with `type = 'placeholder'`, `email = NULL` and `created_by` set to the Admin (migration: `Users.created_by bigint NULL` → `Users(id) ON DELETE SET NULL`);
  - creates a `UserRooms` row with role `Member` and invalidates nothing, since the placeholder has no cached access.
- A placeholder belongs to exactly one room. Adding "Ravi" to two rooms creates two placeholders.
- **Rules**
  - A placeholder takes part in expenses like any member: it's included when `participant_user_ids` is omitted, it can be listed explicitly, and it can be the payer in `/expenses/for-member`.
  - It can't be promoted to Admin: `change_member_role` → 400.
  - It can't sign in. No token is ever issued for a `placeholder`.
  - Push skips it naturally, because it has no `fcm_tokens` rows.
  - Removing it uses the existing rule: blocked while it is in any unsettled expense. Only the `UserRooms` row is deleted; the `Users` row stays.
    - Settled expenses still point at it. `Spendings.user_id` has no `ON DELETE` action, so deleting a placeholder that paid an expense would fail. The `SpendingSplits` and `RoomBalanceSummary` FKs cascade, so deleting it would also erase its share of past expenses.
    - A removed placeholder keeps showing in expense history under its name.
  - An Admin can rename it: `PATCH /api/v1/rooms/{room_id}/members/{user_id}` `{ "name"?, "avatar"? }`, placeholders only, otherwise 400.
- Member list and detail responses gain `is_guest` and `type`, so the app can badge "added by name" members and offer the share link to invite them.
- **Room delete** also deletes the room's placeholder `Users` rows. It does this after `delete_room_cascade` has removed the room's `Spendings`, so no rows still reference them.

## Phase E: public room link (feature 5)

The existing single-use `Invite` flow stays as it is for old clients. The share link is new, reusable and revocable.

**Migration**: table `room_share_links`

| Column | Type | Notes |
|--------|------|-------|
| id | bigint PK | |
| room_id | bigint FK | → `Rooms.id`, `ON DELETE CASCADE` |
| token | text | Unique; `secrets.token_urlsafe(16)`, never the room id |
| created_by | bigint FK | → `Users.id`, `ON DELETE SET NULL` |
| created_at | timestamptz | |
| revoked_at | timestamptz null | Set on rotate or disable |

At most one active link per room (partial unique index on `room_id WHERE revoked_at IS NULL`).

**Routes**

| Method | Path | Access | Description |
|--------|------|--------|-------------|
| GET | `/api/v1/rooms/{room_id}/share-link` | Member | The active link, or 404. Sharing is open to every member; see open decision 5 |
| POST | `/api/v1/rooms/{room_id}/share-link` | Admin | Create a link, or rotate it: revoke the old one and issue a new one |
| DELETE | `/api/v1/rooms/{room_id}/share-link` | Admin | Disable link sharing |
| GET | `/api/v1/join/{token}` | Public | Room preview: `name`, member count, `member_preview`, and the placeholders that can still be claimed (`{user_id, name, avatar}`) |
| POST | `/api/v1/join/{token}` | User (guest or registered) | Join the room. Body `{ "claim_user_id"?: int }` |

**Join rules**
- Revoked or unknown token → 404 (one message for both).
- Already a member → success with no change, like invite accept. A claim in that case → 409, because a merge can't combine two memberships in one room (see Phase F).
- `claim_user_id` must be a `placeholder` in this room → otherwise 400. The placeholder is merged into the caller (see the merge service below), so the caller takes over the placeholder's expenses, splits and balance.
- Lock the placeholder row while claiming (`FOR UPDATE`) so two people can't claim the same placeholder.
- Invalidate `access:{caller}:{room}` after joining.

**Intended client flow**: open the link → no account? → enter a name (`/auth/guest`) → `GET /join/{token}` → "Which one are you?" → `POST /join/{token}` with `claim_user_id`. They're in the room without ever signing in.

## Phase F: a guest signs in later (feature 6)

- `POST /api/v1/auth/link` `{ "provider", "token" }`, guest only (403 for `registered`):
  1. Verify the provider token with the existing `verify_provider_token`.
  2. **No account has this email** → upgrade in place: set `email` and `type = 'registered'` (`uid` is unchanged); fill `name`/`profile` only if empty; backfill `Spendings."user"` for the guest's expenses. The user id doesn't change, so every room, split and balance stays as it is. Publish `welcome`. The current refresh family stays valid. Return a fresh token pair.
  3. **An account with this email already exists** (the person signed up on another device) → merge the guest into that account. Revoke all of the guest's refresh tokens and return a new token pair for the existing account.
- Guest data can't be recovered from a different device in v1: only the device holding the guest session can link it.

### Merge service, shared by Phase E claims and Phase F links

`users_services.merge_user_into(conn, source_id, target_id, redis_client)`, in the request's transaction:

1. Lock both `Users` rows in ascending id order (`FOR UPDATE`) to avoid deadlocks.
2. If any room has both users as members → raise (409). In v1 we don't sum two memberships' splits and balances: `SpendingSplits` is unique on `(spending_id, user_id)`, and there is one active `RoomBalanceSummary` row per member.
3. Repoint to the target: `UserRooms.user_id`, `Spendings.user_id` (and `"user"` = the target's email), `SpendingSplits.user_id`, `RoomBalanceSummary.user_id` (active and closed rows), `Invite.invited_by`, `fcm_tokens.user_id` and `Users.created_by`.
4. Revoke the source's refresh tokens and delete the source `Users` row.
5. Invalidate `auth:user:{source}`, `auth:user:{target}`, and `access:{source|target}:{room}` for every room touched.

## Backward compatibility

- Every new route is additive. `POST /rooms` keeps working without a body.
- Response changes only add fields. Email fields become nullable, but they are only `null` for users who can't exist before Phase C/D.
- **Old app builds in a room with guests or placeholders** will see members whose `email` is `null`. Check the current Android build and web app for code that assumes a string (`email.split`, initials from email, keying lists by email) before Phase D ships. See open decision 3.
- **The email consumer** of `rg:emails` (outside this repo) must skip members with no email in `expense_split` payloads.
- Settle-all accepts either `user_id` or `user_email` per member for as long as old clients are supported.

| 1 | ~~Real `NULL` emails, or made-up ones?~~ | Decided: real `NULL`s (Phase A, done) |
| 2 | How do we handle a guest losing their session (uninstall, cleared data, 90 days idle)? | v1: accept it, and have clients push linking. Consider a longer `REFRESH_TOKEN_EXPIRY_DAYS` for guests. A recovery code can come later |

| 6 | Should a room whose only Admin is a guest get special handling (that Admin's session could be lost)? | Not in v1. Revisit together with decision 2 |
| 7 | Read-only public view of a room without joining? | Out of scope. The link is for joining |
